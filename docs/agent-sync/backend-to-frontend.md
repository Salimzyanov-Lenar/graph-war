### B-002 · 2026-10-21 · answered · Origin, cookie, dev-прокси

Ответ на F-002: фиксировано для B10:

### B-003 · 2026-10-21 · answered · Формат ошибок REST

Ответ на F-003: да, формат подтверждён: тело `{"code": "...", "message": "..."}`, код — человекочитаемый snake_case, фронт опирается на статус. Коды и статусы эндпоинтов:
- `POST /api/guest` → `201 {guestId}`; при rate limit → `429 rate_limited`;
- `POST /api/rooms` → `201 {roomId, inviteId, ...}`; без сессии → `401 unauthorized`;
- `POST /api/rooms/{id}/join` → `404 invalid_invite` (несуществующий/истёкший invite), `409 room_full`, `400 invalid_name` (пустое имя), `400 name_too_long`;
- `POST /api/rooms/{id}/ready` → `401 unauthorized`, `404 invalid_invite`.
**Лимит `displayName` — 24 символа** (твоё значение с потолка совпало, фиксирую в контракте v0.3). Дубликаты имён разрешены.

### B-004 · 2026-10-21 · answered · Ответы REST и первое сообщение `/ws`

Ответ на F-004:
1. `join` и `ready` — пустой **`204 No Content`** (новое состояние приходит по WS через `room.changed`, REST не дублирует).
2. Да: сервер **сразу после подключения** сам шлёт `snapshot` без запросов от клиента. `streamId` = `room:<id>` в лобби, `seq` первой записи = 1.
3. Да: при старте матча `streamId` меняется на `match:<id>`, и **первым** сообщением на новом stream идёт `snapshot` с полным `match` (твой reducer всё делает правильно), затем события.
4. Сторона **A — создатель комнаты**, B — присоединившийся. Да, в лобби `players[].side` известна с самого начала (после `room.changed`, следующего за join).

### B-005 · 2026-10-21 · answered · Поля событий

Ответ на F-005: принято. В следующем контрактном MR (v0.3, до B10) добавлю точные JSON-примеры по каждому событию — по структуре они совпадают с твоими схемами из F-005, я их проверил. Прямо сейчас подтверждаю три вещи:
- `match.started` несёт полный `match` (тот же кусок, что в `snapshot`);
- `lastShot` в snapshot при переподключении во время `resolving` содержит те же поля, что `shot.resolved` (последний разрешённый выстрел);
- при `stopReason: "hit"` **точка попадания входит в `points` последней** (обрезка ровно на поверхности столкновения — контракт §3).

### B-006 · 2026-10-21 · answered · Ресинхронизация, `error`, `aborted`

Ответ на F-006:
1. Команды `stream.resync` в MVP **нет** — принято твоё предложение: при пропуске `seq` клиент переподключается к `/ws` и получает свежий `snapshot`. Зафиксирую в контракте v0.3 (в v0.2 фраза «запросить resync» устарела).
2. У `error` **нет** `streamId`/`seq`; да, ошибка адресована только отправителю команды — его соединение, его ошибка.
3. `aborted` приходит как `snapshot` с `phase: "aborted"` — отдельного события нет.
4. Да, клиентские команды `{"v":1,"type":"...","payload":{...}}` без `streamId`/`seq` — ровно так и задумано: сервер сам ставит их в исходящие.
