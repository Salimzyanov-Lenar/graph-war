# Graphwar: небольшой стек — исследовательская заметка

**Статус:** проверка официальной документации и исходников, не окончательное архитектурное решение. Контекст: сначала законченный онлайн-матч по ссылке вдвоём (backend + frontend), desktop browser, упрощённые траектории `y=f(x)`; аккаунты и лидерборд позднее. Репозиторий не изменялся, пакеты не устанавливались, интеграционные тесты не запускались.

**Вывод:** стек подходит как кандидат без отдельной realtime-платформы и игрового фреймворка. Его части решают разные задачи; подключать весь список до первого матча необязательно. Это инженерная оценка для обсуждения, не принятое за пользователя решение.

## 1. Назначение компонентов

| Компонент | Что предоставляет | Применение в этом проекте — предложение |
|---|---|---|
| **Go + `net/http`** | Стандартный HTTP-сервер, обработчики и маршрутизатор `ServeMux`.[1] | HTTP API, вход в комнату, точка подключения WebSocket. Для небольшого API начать можно без стороннего роутера. |
| **`chi` — опционально** | Лёгкий роутер, совместимый с `net/http`, с композицией маршрутов и middleware.[2] | Добавить ради удобства групп маршрутов; это надстройка над `net/http`, а не замена HTTP-сервера. |
| **PostgreSQL** | Реляционная БД и SQL.[17] | Постоянные данные: будущие пользователи, сессии, результаты. Нужна ли сохранность текущего матча уже в первом этапе — отдельное решение. |
| **`pgx` / `pgxpool`** | Драйвер PostgreSQL для Go; `pgxpool` — concurrency-safe пул соединений.[3][25] | Выполнение SQL из backend. Успешное создание пула ещё не подтверждает соединение с БД: документация требует отдельно проверить получение соединения.[25] |
| **`sqlc`** | Генерация Go-методов доступа к данным из SQL; поддерживается `sql_package: pgx/v5`.[4] | Типизированные запросы без ORM. Это инструмент генерации, не отдельный сервис и не система миграций.[24] |
| **`goose`** | Последовательные миграции схемы через SQL или Go.[5] | Для старта достаточно SQL-миграций. `sqlc` умеет читать миграции goose, игнорируя Down; порядок имён должен совпадать с лексикографическим.[24] |
| **`github.com/coder/websocket`** | WebSocket для Go, `context.Context`, JSON-помощники `wsjson`, ping/pong и закрытие соединения.[7] | Команды игроков и события матча. Формат сообщений, reconnect и восстановление состояния остаются задачами приложения. |
| **TypeScript + Vite** | TS — статическая проверка типов; Vite — dev-сервер/HMR и production-сборка.[11][12] | Разработка frontend. Vite сам **не проверяет типы**: нужен отдельный шаг вроде `tsc --noEmit`; TS-типы не заменяют проверку входящих сетевых данных.[23][11] |
| **React + PixiJS** | React предоставляет механизм синхронизации с внешним виджетом через Effect; Pixi — renderer, сцена, canvas и ticker.[13][14] | Разделить DOM-интерфейс (формы, кнопки, статус) и отрисовку поля/траектории. Pixi не должен становиться источником правил матча. |
| **Vitest** | Тестовый фреймворк, использующий инфраструктуру Vite.[15] | Проверки чистой TS-логики, преобразований координат, обработки сообщений. |
| **Playwright** | E2E в реальных браузерах; независимые browser contexts изолируют cookies и storage.[16][22] | Полный матч двух игроков проверять **двумя contexts**, а не двумя вкладками одного профиля. |

Практический вывод для слоя данных: `goose` меняет схему, `sqlc` генерирует методы, `pgx` выполняет запросы. Генерация не заменяет применение миграций и проверки на настоящем PostgreSQL.[4][5][24]

## 2. WebSocket: Origin, cookies и время жизни

- **Cookie-аутентификация совместима с браузерным WS.** Стандарт задаёт handshake с `credentials mode: include`; отправка конкретной cookie зависит от её атрибутов и политики браузера. Конструктор принимает URL и subprotocols, но не произвольный `Authorization` header.[20] Проверять сессию и право входа до upgrade; авторизацию каждой игровой команды проверять отдельно. CORS-настройка HTTP API не заменяет проверку WS `Origin`.[19]
- **Важная тонкость `coder/websocket`.** В проверенном исходнике `v1.8.15` отсутствующий `Origin` допускается, а совпадающий с `r.Host` origin-host разрешён независимо от схемы; `OriginPatterns` добавляет разрешения, а не сужает это поведение.[26] Шаблон без `://` сопоставляется с host, с `://` — с `scheme://host`.[7] Поэтому для строго браузерного endpoint разумно отдельно проверить точный разрешённый origin, включая схему и порт, до `Accept`; отсутствующий/`null` origin не разрешать без явной необходимости. Не включать `InsecureSkipVerify` и не разрешать `*` ради удобства разработки. Это применение рекомендаций OWASP к проверенному поведению библиотеки.[19][26]
- **Одна только успешная аутентификация недостаточна.** Нужны ограничения размера/частоты сообщений и очередей медленных клиентов, закрытие при logout/истечении сессии; публичный транспорт — HTTPS/WSS.[19] У coder должен постоянно работать один reader для обработки control frames; параллельные `Read`/`Reader` недопустимы, а `Ping` требует работающего reader.[7] Задать отдельный жизненный цикл соединения: документация предупреждает о `r.Context()` после `Accept`; истечение контекста операции закрывает соединение.[7]
- **Упростить развёртывание можно единым origin** для страницы, API и WS — это рекомендация, не обязательное требование. В разработке Vite умеет проксировать HTTP и WS, но **не проверяет origin проксируемого WS**; `rewriteWsOrigin` может обходить защиту backend, поэтому не использовать его как исправление отказа handshake.[27] Настройки прокси и allowlist должны сохранять возможность проверить настоящий origin страницы.

## 3. Будущие аккаунты: Argon2id и серверные сессии

- **Пароли:** `golang.org/x/crypto/argon2.IDKey` реализует Argon2id, но возвращает байты, а не готовую систему регистрации/проверки паролей.[8] Нужны уникальная случайная соль, хранение алгоритма/параметров/соли/хеша, например в PHC-формате, и возможность повысить стоимость при следующем входе.[8][10]
- **Параметры не копировать без измерений.** OWASP рекомендует минимум **19 MiB памяти, 2 прохода, параллелизм 1**; у Go `IDKey` параметр памяти задаётся в **KiB**, а пример в документации использует другой, значительно более дорогой профиль RFC.[8][10] Подобрать стоимость под сервер и ограничить частоту/параллелизм входов; это предложение для защиты от перегрузки, а не результат бенчмарка.
- **В cookie — непрозрачный случайный идентификатор, данные сессии — на сервере.** PostgreSQL можно использовать как уже имеющееся хранилище. Для токена нужен CSPRNG; хранение одностороннего verifier/hash снижает риск повторного использования токенов при утечке чтения БД.[9] Пароль и случайный session token — разные сущности: не применять дорогой password hashing механически к каждому запросу.
- **Защита cookie:** `HttpOnly`, `Secure`, явный `SameSite`; `__Host-` требует `Path=/` и отсутствия `Domain`.[9] `Lax` или `Strict` выбирать с учётом захода по внешней ссылке: Lax допускает безопасную top-level навигацию, Strict — нет.[9] `SameSite` не заменяет CSRF-защиту изменяющих HTTP-запросов, а `HttpOnly` не препятствует отправке cookie браузером.[9] Нужны ротация ID при входе/смене привилегий, серверное истечение срока и отзыв при logout; для уже открытых WS отзыв тоже должен действовать.[9][19]

Аккаунты и Argon2id можно отложить до соответствующего этапа. Однако отсутствие аккаунтов **не означает отсутствие контроля доступа** к комнате и месту игрока: гостевая идентификация и право выполнить ход требуют отдельного договора.

## 4. PixiJS внутри React: главное место для утечек

**Проверенные факты:** PixiJS 8.x создаётся через `new Application()`, затем асинхронный `init()`; canvas доступен после инициализации.[14] React Strict Mode выполняет дополнительный цикл setup → cleanup в development.[13] У Pixi `destroy()` управляет освобождением ресурсов, но по умолчанию сохраняет canvas; уничтоженный экземпляр повторно использовать нельзя.[21]

**Практические выводы для интеграции:**

1. Владеть Pixi-приложением в отдельном компоненте/адаптере; создавать его в Effect, хранить в ref, не пересоздавать на каждый React render. Не передавать каждый кадр анимации через React state.
2. Обработать гонку **unmount до завершения `await init()`**: устаревшая инициализация не должна добавлять canvas; после завершения освободить именно её экземпляр. Не вызывать обычный cleanup так, будто асинхронная инициализация уже закончилась.
3. Убирать собственные обработчики/ticker callbacks/наблюдатели и уничтожать принадлежащие компоненту ресурсы, явно удаляя canvas. Общие textures нельзя безусловно уничтожать вместе с одной сценой.
4. Проверить повторный mount/unmount и Strict Mode: один canvas и один активный цикл; отдельно — resize и масштабирование координат. `resolution`, `autoDensity`, `resizeTo` предоставляются Pixi, но согласование экранных и игровых координат остаётся задачей приложения.[14]

## 5. Что не добавлять без подтверждённой потребности

Ниже — **инженерные рекомендации из ограничений задачи**, а не требования библиотек:

- **Redis:** для одного Go-процесса не является условием матча по ссылке. Память процесса может хранить активные комнаты, PostgreSQL — постоянные данные. Но потеря комнат при рестарте недопустима, пока пользователь явно не согласовал такое поведение; восстановление и несколько серверов требуют отдельного решения.
- **ORM:** не нужен поверх `pgx + sqlc`, если устраивает SQL-first подход. Не добавлять второй способ описания той же модели без конкретной задачи.
- **Физический движок:** для `y=f(x)` сначала нужны ограниченный разбор выражений, численное построение траектории и проверки пересечений, а не симуляция rigid bodies. Движок не решает разрывы функций, ограничения вычислений и согласованность результата Go/TS.
- **Полные аккаунты, JWT-инфраструктура, лидерборд, matchmaking и mobile-first:** не блокируют подтверждённый первый этап. Гостевой доступ, TLS, валидация сообщений и корректное завершение матча — не то же самое, что будущая регистрация.

**Для будущих маленьких проверяемых задач:** отдельно согласовать поведение при reconnect/рестарте, грамматику и пределы вычисления формул, авторитетный расчёт результата, контракт сообщений и origin-развёртывание. Затем полезны проверки: матч двумя browser contexts; отклонение чужого Origin/неправомерного хода; отсутствие дублирующихся Pixi canvas после перемонтирования. Это предложенные проверки, они здесь не выполнялись.

**О версиях:** номера latest не определялись и не утверждаются. Для нюансов origin изучен исходник coder `v1.8.15`, для Pixi — руководство 8.x; это границы проверки, не рекомендация конкретного pin. Страницы sqlc по `/stable/` сами помечены как документация старого релиза. Совместимые версии Go/Node/пакетов и peer dependencies нужно закрепить и проверить при реализации; документальная совместимость не равна собранному и протестированному приложению.
